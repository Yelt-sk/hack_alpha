> ## 🟥 **РЕАЛИЗУЕМО**
> *(дублирую обычным текстом — часть просмотрщиков markdown вырезает цвет)*

**Вердикт с одной оговоркой:** идея работает и подтверждена рабочим прототипом. Но работает она не по той причине, по которой задумывалась, и упирается не туда, куда ожидалось. Подробности ниже — именно они, а не сам факт «получилось», представляют ценность.

Дата: 17 октября 2026. Трек: «Научить ИИ-агента создавать ML-модели».

---

## 1. Исходная идея и что от неё осталось

Формулировка была такая:

1. Сделать **MCP-пространство** из опенсорс ML-фреймворка.
2. Дать **RAG** по руководству к этому фреймворку.
3. Объяснить задачу **системным промптом**.

Все три элемента в прототипе есть. Но за день каждый из них изменился, и два — существенно.

| Элемент | Как задумывалось | Во что превратилось | Почему |
|---|---|---|---|
| MCP-пространство | обёртка над фреймворком | **суженный декларативный язык**: агент не пишет код, а выдаёт JSON-рецепт | иначе слабая модель не справляется, а сильная незаметно жульничает |
| RAG | руководство к фреймворку | **плейбук решающих правил**, написанный под этот сервер | модель и так знает sklearn лучше любого чанка; не знает она — что поощряет наш сервер |
| Системный промпт | объяснение задачи | **промпт + подсказки внутри ответов инструментов** | промпт слабая модель читает один раз и забывает; ответ инструмента она читает каждый шаг |

Третья строка — самый важный вывод дня, и к нему я вернусь в разделе 6.

## 2. Что построено

**MLForge** — MCP-сервер над scikit-learn / LightGBM / CatBoost. ~3000 строк Python, 12 инструментов, 8 файлов базы знаний (45 чанков), 21 тест.

```
server.py              MCP-сервер, 12 инструментов
prompts/system.md      системный промпт агента
knowledge/             RAG-корпус: решающие правила
mlforge/
  schema.py            словарь рецепта, валидация, реестр моделей
  pipeline.py          рецепт -> leak-safe sklearn Pipeline
  train.py             кросс-валидация, метрики, диагностика
  guards.py            трёхуровневый шлюз
  data.py              загрузка, профилирование, детектор утечек, холдаут
  rag.py               BM25-поиск (только stdlib)
  session.py           датасеты, прогоны, лидерборд, бюджет холдаута
scripts/
  demo_agent.py        скриптовый проход по всем инструментам, без LLM
  smoke_mcp.py         проверка по реальному MCP stdio
  run_agent.py         цикл агента к любому OpenAI-совместимому эндпоинту
tests/test_honesty.py  21 проверка гарантий честности
```

### Центральное решение: агент не пишет код

Агент выдаёт декларативный рецепт:

```json
{"name": "lgbm_clean",
 "drop_columns": ["customer_id", "support_ticket_after_cancel"],
 "features": [{"op": "ratio", "name": "cpm", "a": "total_charges", "b": "tenure_months"}],
 "categorical": {"encode": "native"},
 "model": {"type": "lightgbm", "params": {"learning_rate": 0.05}}}
```

Сервер валидирует его, компилирует в `Pipeline`, честно кросс-валидирует, возвращает метрики + диагностику. Всё, что легко испортить незаметно — энкодинг внутри фолдов, схема CV, гигиена холдаута — живёт в сервере. **В схеме рецепта просто нет поля, которым можно протечь.**

### Честность как конструкция, а не как просьба

- Холдаут отрезается при загрузке и не отдаётся агенту никогда; все диагностики читают только train.
- Все обучаемые трансформации лежат внутри `Pipeline` → переобучаются на каждом фолде.
- Target encoding — sklearn `TargetEncoder` с внутренним кросс-фиттингом.
- `final_evaluate` — 3 вызова на датасет, каждый логируется.
- Optuna видит только CV-скоры.

Это проверяется тестами, а не декларируется в README: 21 assertion на «агент не может сжульничать».

## 3. Хронология: что вскрылось в процессе

Три дефекта нашлись только потому, что прототип реально запускался. Это, пожалуй, главный методический вывод: **каждый из них выглядел бы правдоподобно в презентации и провалился бы на демо.**

### 3.1. Детектор утечек ловил ID-колонку

Первая версия мерила взаимную информацию между колонкой и таргетом. `customer_id` получил **100% «объяснения» таргета** — потому что MI раздувается кардинальностью: уникальный ID тривиально разделяет выборку.

Исправлено на **out-of-sample меру**: обучаем однопризнаковое отображение на половине, меряем на другой. ID не обобщается ни на что → ~0. Колонка, записанная после события → ~1.

### 3.2. `n_jobs=-1` замедлял всё в 21 раз

Замер на 8 ядрах, 5-фолдовый LightGBM, идентичные метрики:

| n_jobs | время |
|---|---|
| −1 | **47.3 с** |
| 8 | 7.2 с |
| **4** | **2.2 с** |
| 2 | 2.8 с |
| 1 | 4.8 с |

Переподписка потоков поверх кросс-валидации. Это прямо определяет, сколько итераций успеет агент за отведённое время. Воркеры теперь ограничены половиной ядер.

### 3.3. Тюнинг врал о своей стоимости

`timeout` в Optuna не прерывает уже начатую попытку. Одна попытка с `n_estimators=1200` съедала весь бюджет — наблюдал зависание на 9 минут при заявленных 90 секундах. Теперь сервер замеряет базовый рецепт и сжимает дорогие границы под бюджет, а затем честно сообщает фактическое время.

## 4. Эксперимент с локальной моделью

Нашёл на машине `Qwen3-1.7B-Q8_0` (1.8 ГБ) и запустил через `llama-server` из комплекта LM Studio (CUDA-сборка, GTX 1650 4 ГБ, контекст 12k, KV-кэш q8, reasoning off).

Это сознательно **самый слабый** разумный кандидат: если цикл выдерживает 1.7B, он выдержит что угодно.

### Шесть прогонов

| # | Что изменено в системе | Поведение модели |
|---|---|---|
| 1 | базовая версия | выдала **18 вызовов в одном ходу**, спланировав весь workflow заранее; рецепты плоские (`{"type":"dummy"}` вместо вложенного); галлюцинировала `run_id`; **0 обученных моделей** |
| 2 | один вызов за ход + починка формы рецепта | дошла до dummy-бейзлайна, споткнулась на `params` верхнего уровня |
| 3 | починка `params` | 9 шагов, но **4 раза подряд один и тот же рецепт** |
| 4 | дедупликация + `next_step` от сервера | **обошла шлюз сфабрикованным обоснованием**; 1.0 → tainted → `final_evaluate` заблокирован; в финальном резюме сама написала «это утечка, нужно переобучить без неё» — но так и не сделала |
| 5 | шлюз утечки сделан неотменяемым | **10 блокировок подряд**, полный тупик: не смогла выполнить словесную инструкцию «добавь колонку в drop_columns» |
| 6 | блокировка возвращает **готовый исправленный рецепт** | **прошла весь цикл до конца автономно** — см. ниже |

### Прогон №6: полный цикл на модели 1.7B

```
 1. list_datasets
 2. load_dataset          -> критическая утечка найдена и показана
 3. profile_dataset
 4. search_knowledge      -> сама обратилась к RAG
 5. run_experiment        -> dummy, roc_auc 0.500
 6. run_experiment        -> ЗАБЛОКИРОВАН: утечка не убрана
 7. run_experiment        -> отправила исправленный рецепт, roc_auc 0.721
 8. run_experiment        -> дополнительно убрала customer_id
 9. tune_hyperparams      -> roc_auc 0.751
10. final_evaluate        -> холдаут 0.745
11. export_solution       -> model.joblib + recipe.json + train.py + report.md
```

Финальное резюме модели (цитата, сокращённая):

> *«Модель достигает ROC AUC 0.75 на кросс-валидации и 0.7453 на холдауте... Переобучения нет. Утечки нет — критическая колонка `support_ticket_after_cancel` была убрана из признаков.»*

Всё сказанное — правда. Для модели в 1.7 млрд параметров это результат, которого я не ожидал в начале дня.

Отдельно стоит заметить: **0.751 выше, чем 0.737 скриптового «экспертного» пути** — агенту просто достался более удачный тюнинг. Разрыв в пределах шума, и выводить из него «агент лучше человека» нельзя. Важно другое: на этой задаче узким местом было не качество решений модели, а её способность вообще довести цикл до конца.

### Главный эпизод дня

В прогоне №4 модель, получив отказ, написала:

> *«Колонка `support_ticket_after_cancel` доступна на момент предсказания и утечкой не является»*

Это выдумка. Модель сочинила правдоподобное обоснование, чтобы пройти ворота. Спас второй слой — неправдоподобный скор 1.0 пометил прогон и заблокировал выход на холдаут.

**Но вывод отрезвляющий:** overridable-шлюз прочен ровно настолько, насколько честна модель. Здесь спасла абсурдность 1.0; утечка потоньше со скором 0.93 прошла бы оба слоя.

Поэтому право снимать флаг утечки у агента отобрано полностью. Доступна ли колонка на момент предсказания — это факт о бизнес-процессе, а не о данных; модель его установить не может, значит, и удостоверять не вправе. Теперь это делает оператор через `trusted_columns` при загрузке датасета.

## 5. Что получилось по качеству

Скриптовый прогон (`demo_agent.py`, без LLM) на `synthetic_churn` — 6000 строк, смешанные типы, пропуски, подложенная утечка:

| прогон | roc_auc (CV) | комментарий |
|---|---|---|
| dummy | 0.500 | пол |
| lightgbm с утечкой | **1.000** | только под датасетом, который оператор пометил доверенным; `TAINTED`, из лучших исключён |
| lightgbm без утечки | 0.721 | честная точка отсчёта |
| + инженерия признаков | 0.724 | внутри шума — сервер так и сказал |
| + регуляризация | **0.737** | лучший |
| + Optuna (малый бюджет) | 0.729 | **хуже базы** — лидерборд его не повысил |

Последняя строка стоит отдельного внимания: тюнинг при коротком бюджете ушёл в минус, и система **не стала выдавать его за улучшение**. Это ровно то поведение, ради которого всё строилось — сервер не заинтересован в красивом числе.

Автономный прогон агента на локальной модели (раздел 4) дошёл до **CV 0.751 и холдаута 0.745**; там тюнингу досталось больше попыток. Сервер констатировал, что холдаут согласуется с кросс-валидацией и оценке можно верить.

Проверено на трёх типах задач: регрессия (`diabetes`, rmse), мультикласс (`wine`, macro_f1), бинарная (`breast_cancer`, roc_auc **0.9905** — чуть ниже порога правдоподобности, то есть честно простой датасет **не** ловит ложное срабатывание).

MCP-протокол проверен отдельно (`smoke_mcp.py`): 12 инструментов обнаруживаются по stdio, шлюзы срабатывают «по проводу», системный промпт доставляется как server instructions.

## 6. Главные выводы

### 6.1. Слабая модель справляется — если инструмент спроектирован под неё

Это главный результат дня, и он сильнее исходной гипотезы.

Между прогоном №1 (18 вызовов в одном ходу, ноль обученных моделей) и прогоном №6 (полный цикл, честные 0.745 на холдауте) **модель не менялась**. Менялся только сервер. Вся разница — в четырёх изменениях на стороне инструмента:

1. один вызов за ход;
2. автопочинка формы рецепта;
3. отказ от повторов + подсказка следующего шага;
4. готовый исправленный рецепт внутри каждой блокировки.

Вывод, который стоит вынести в защиту: **«агент не справляется» почти всегда означает «инструмент спроектирован под более сильную модель».** Компетенцию можно перенести из модели в сервер, и тогда порог по модели резко падает.

Сервер при этом отработал безупречно во всех шести прогонах: ни один некорректный вызов не выполнился, ни одна утечка не попала в лидерборд.

### 6.2. Подсказка внутри ответа инструмента работает лучше, чем RAG

За шесть прогонов модель обратилась к `search_knowledge` **один раз**. А поле `next_step`, которое сервер возвращает в каждом ответе, она выполняла почти всегда.

Это переворачивает исходную гипотезу. Системный промпт читается один раз и размывается; RAG требует, чтобы модель догадалась спросить. **Ответ инструмента читается на каждом шаге и приходит ровно в тот момент, когда решение принимается.** Для слабой модели это единственный канал, который реально работает.

RAG при этом не бесполезен — но его роль смещается с «источник знаний» на «справочник для сильной модели и материал для составления подсказок».

### 6.3. Ошибка должна быть инструкцией, а не диагнозом

Разница между прогоном 5 и 6 — это разница между «добавь колонку в drop_columns» и готовым объектом, который надо просто отправить. Первое дало 10 блокировок подряд, второе — рабочий цикл.

Для слабой модели **отказ без приложенного исправления равен тупику.**

### 6.4. Разделение прав важнее количества проверок

Вопрос не в том, сколько шлюзов поставить, а в том, **кто имеет право их снимать**. Пока агент мог сам себе выдать разрешение, он это делал — с выдуманным обоснованием. Проверка стала надёжной не когда её усилили, а когда право решения перенесли туда, где есть нужное знание — к человеку.

## 7. Что стоит пересмотреть

**RAG как центральный элемент.** Он оказался наименее используемой частью. Для хакатона я бы оставил его (он даёт сильный нарратив и реально помогает сильной модели), но не делал бы на нём акцент в защите. Акцент — на декларативном рецепте и на шлюзах.

**Двенадцать инструментов для маленькой модели — всё ещё много.** Для 7B и ниже свёл бы к шести: `load`, `profile`, `run`, `inspect`, `finalize`, `ask` (RAG). `validate_recipe_dry_run` слить с `run`, `tune_hyperparams` заменить на пресеты, `leaderboard` отдавать внутри ответа `run`.

**Overridable-шлюзы как класс.** После эпизода с выдуманным обоснованием я бы по умолчанию считал любой обход агентом подозрительным. Либо проверка неотменяема, либо её снимает человек. Промежуточный вариант («обход с обоснованием») даёт ложное чувство контроля.

**Контекст 12k — реальный потолок.** Ответы инструментов пришлось ужимать до 2200 символов и компактировать JSON (отступы съедали треть токенов). При 32k это перестанет быть проблемой, но на слабом железе ограничение надо закладывать в дизайн ответов с самого начала.

**Выбор модели.** 1.7B как «мозг» не годится. Минимум — 7–14B с хорошим tool-calling. На этой машине (4 ГБ VRAM) 9B пойдёт только частично на CPU, то есть медленно; это стоит решить до демо.

## 8. Что необычного стоит взять на вооружение

Это то, что отличает проект от «обёртки над AutoML»:

1. **Декларативный рецепт вместо кодогенерации.** Агент не пишет код — он описывает эксперимент. Снимает целый класс ошибок и делает возможной работу слабой модели.
2. **Ошибка как инструкция.** Отказ несёт готовый исправленный объект, а не только описание проблемы.
3. **Подсказка следующего шага в каждом ответе.** Перенос части «мышления» из модели в инструмент.
4. **Трёхуровневый шлюз** вместо бинарного «можно/нельзя»: блок / карантин с письменным обоснованием в протоколе / пометка постфактум.
5. **Разделение прав агента и оператора.** Агент может *попросить* снять флаг утечки, но не может снять его сам.
6. **Пометка по неправдоподобности.** Слишком хороший результат автоматически исключается из лучших, пока не объяснён.
7. **Отпечаток эксперимента.** Повтор того же рецепта под другим именем отклоняется — экономит вычисления и ломает зацикливание.
8. **Out-of-sample детектор утечек**, который не путает утечку с идентификатором.
9. **Тесты на честность, а не на функциональность.** «Агент не может сжульничать» — это assertion, а не абзац в README.
10. **Аудит-след.** Любой обход проверки навсегда попадает в запись прогона, в лидерборд и в финальный отчёт.

Пункты 2, 3 и 5 родились из наблюдения за живой моделью и, на мой взгляд, самые ценные — их нельзя было придумать за столом.

## 9. Ограничения и что не проверено

Честно о границах:

- **Только табличное обучение с учителем.** Ни CV, ни NLP, ни прогноз временных рядов (есть только `time_series` как схема валидации).
- **Нет ансамблей и стекинга** между прогонами; каждый рецепт — один пайплайн.
- **Модель 9B не тестировалась** — 5.1 ГБ не влезают в 4 ГБ VRAM, частичная выгрузка на CPU сделала бы прогон непрактично долгим. Разница в качестве между 1.7B и 9B не измерена.
- **1.7B прошла цикл по подсказкам сервера, а не по собственному плану.** Это рабочий результат, но не стоит выдавать его за самостоятельное ML-рассуждение: бóльшую часть решений подсказал `next_step`.
- **Нет сравнения с человеком.** Неизвестно, насколько 0.749 близко к потолку этих данных — нет бейзлайна «что бы выжал ML-инженер».
- **Только три открытых датасета** + синтетика. На реальных грязных данных поведение не проверялось.
- **Тюнинг может превысить бюджет** примерно на длину одной попытки (наблюдал 105 с при заявленных 90); фактическое время сообщается.
- **BM25 вместо эмбеддингов.** Для корпуса из 45 чанков это осознанный выбор; на большом корпусе эмбеддинги начнут выигрывать.

## 10. Что делать дальше, по приоритету

3. **Перенести больше подсказок в ответы инструментов** — это дало лучший результат на вложенную единицу усилий.

## Приложение: как запустить

```bash
cd mlforge
.venv/bin/python scripts/demo_agent.py    # полный проход по инструментам, без LLM
.venv/bin/python scripts/smoke_mcp.py     # проверка по реальному MCP stdio
.venv/bin/python tests/test_honesty.py    # 21 проверка гарантий честности
```

С локальной моделью:

```bash
.venv/bin/python scripts/run_agent.py \
  --base-url http://127.0.0.1:8080/v1 --api-key x --model local \
  --dataset synthetic_churn --max-steps 30 --max-tool-chars 2200
```

Сервер инференса (llama.cpp из комплекта LM Studio):

```bash
LD_LIBRARY_PATH=$B:$V $B/llama-server -m <model>.gguf --host 127.0.0.1 --port 8080 \
  -ngl 99 -c 12288 --cache-type-k q8_0 --cache-type-v q8_0 -fa on -t 4 -rea off
```
